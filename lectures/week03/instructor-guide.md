## 왜 이걸 배워야 할까? (학생에게 전달할 메시지)

오늘은 `if`로 판단하고, `for`로 하나씩 꺼내 세고, 판정 규칙을 함수 하나(`check_range`)로 만든 뒤, Orange Select Rows로 같은 조건의 행을 골라 개수를 비교한다.

## 강사 설명 포인트

- `=`와 `==`를 칠판에 나란히 적는다. `=`는 1차시의 "저장하라", `==`는 "같은가?"라는 질문이다.
- 들여쓰기는 "여기까지가 `if` 안"이라는 표시다. 1단계 두 번째 셀의 `print("채점 끝")`이 들여 쓰지 않아 늘 실행된다는 점을 짚는다.
- `for`의 세기는 오늘 가장 큰 벽이다. 3단계 세 번째 셀(한 바퀴씩 `print`)의 출력(72 → 0, 85 → 1, 90 → 2, 64 → 2, 88 → 3)을 손으로 짚으며 "0에서 시작해야 아직 하나도 안 셌다에서 출발한다"를 말한다. 실습은 `count = count + 1` 한 가지 모양으로 통일한다.
- 함수는 "가게에 붙여 둔 규칙 카드"로 설명한다. 괄호 안 이름 `point`는 "넣어 준 값을 받는 자리"다 — `judge_score(85)`면 85가, `judge_score(64)`면 64가 들어간다. 5단계에서 `for`가 꺼낸 `score`가 함수 안에서 `point`로 쓰인다는 점을 짚는다.
- 중첩 `if`(문제 3-3)는 5단계 끝 한 줄로만 예고한다. "바깥 조건과 안쪽 조건을 둘 다 만족할 때만".
- 반도체 확인에서 **규격**(스펙)을 소개한다. 규격 = 사람이 미리 정해 둔 허용 범위(피자 레시피의 오븐 온도 범위)이고, 실제로는 공정·제품마다 따로 있다. 이 과정은 모든 기록에 **연습용 기준** 295~305도 하나를 쓴다. 데이터에서 계산하는 관리 한계(8차시)와는 다른 말이다. 같은 범위를 여러 이름으로 섞어 부르지 않고 '연습용 기준'으로만 부른다.
- **두 가지 판정을 분리**한다. `check_range`가 내는 "범위 안/범위 밖" = 연습용 기준으로 본 판정, `합격여부` = 공장 검사의 실제 결과. 학생이 "불합격"을 두 뜻으로 쓰지 않게, 코드 쪽은 늘 "범위 밖"이라고 부른다.
- 데이터 소개에서 두 가지를 꼭 말한다. ① 한 로트는 여러 공정을 거치므로 같은 로트번호가 여러 행에 나온다(합격여부도 행마다). ② 설비↔공정 짝은 교육용 가상이다 — 실제로는 설비마다 맡는 공정이 정해져 있다. 설비별 값 차이를 "같은 작업의 측정 변동"으로 설명하지 않는다.
- 6단계 출력에서 "범위 밖 / 합격여부 1"인 줄 3개를 손으로 짚는다. "기준 밖이면 불량일까요?"라고 묻고 "기준 밖 = 살펴볼 후보"로 정리한다. 이 차시는 "원인" 이야기를 하지 않는다 — 기준이 후보를 골라 주는 거름망이라는 데까지만 간다.
- 워밍업과 대비: 미세먼지 등급은 PM10 값으로 **정의된** 판정이라 Select Rows 조건과 딱 맞지만, 반도체 `합격여부`는 온도로 정한 값이 아니라 딱 맞지 않는다. 또 미세먼지는 높은 쪽만 문제(한쪽 기준), 온도 기준은 양쪽(`is outside`)이다. "미세먼지 등급 = 규격"처럼 등식으로 말하지 않는다.
- 실습지 문제 3·4의 답(12건 · 3건)은 결과 정리 절에 접혀 있다. 강의 "AI로 한 걸음 더"의 출력도 접혀 있다(높음 + 낮음 = 12). 실습지를 푼 뒤에 연다.
- **강사만 알 것**: `합격여부`는 온도로 정한 값이 아닌 가상 값이다. 기준 안 18건은 모두 합격이므로 "기준 안이어도 불합격이 있다"고 말하면 데이터와 맞지 않는다.

- `is greater than`은 "초과"(80 자체는 빠짐), `is at least`가 "이상"이다. 학생이 헷갈리면 파이썬의 `>`와 `>=`에 대응시켜 준다.
- Data Table의 열 순서는 CSV와 다르다(`합격여부 · 로트번호 · 공정명 · 설비번호 · 온도_C`). 대기 데이터는 `날짜`(meta)가 맨 앞이다.

## 학생들이 자주 찾아볼 질문과 보충 설명

- **파이썬 들여쓰기 이유**: AI가 "스페이스 4칸이 아니면 무조건 오류"라고 단정하는 경우가 있다. 한 블록 안에서 칸 수가 일정하면 동작하지만, 이 과정은 4칸으로 통일한다고 말해 준다.
- **공정 규격 스펙 뜻**: AI가 규격(미리 정한 요구 범위)과 관리 한계(데이터에서 계산한 범위, UCL/LCL)를 섞어 설명할 수 있다. 오늘은 "사람이 미리 정해 둔 허용 범위, 공정·제품마다 따로"까지만 확인하고, 관리 한계는 8차시에 다룬다고 넘긴다. AI가 실제 공정의 규격 숫자를 말하면 "제품·설비마다 다르고 확인할 수 없는 숫자"라고 보충한다.
- **온도만 보고 불량 판단 문제점**: AI가 "온도가 불량의 원인"처럼 단정하는 문장을 섞을 수 있다. 오늘의 결론은 "온도 하나로는 다 설명되지 않는다, 기준 밖은 살펴볼 후보"까지다.
- **미세먼지 PM10 등급 기준**: 검색 결과에 PM2.5 기준(숫자가 다르다)이나 다른 나라 기준이 섞여 나올 수 있다. 오늘 데이터는 PM10 기준 좋음 0~30 · 보통 31~80 · 나쁨 81~150 · 매우나쁨 151 이상을 빌린 교육용 가상 측정값이다.

## 예상 오개념

- `=`와 `==`를 같은 뜻으로 읽음 → `=`는 저장, `==`는 질문. `if score = 80:`은 `SyntaxError`.
- 세는 변수를 `for` 안에서 0으로 만들어도 된다 → 매번 0으로 돌아가 마지막 값만 센다(조용한 오답).
- 함수를 정의하면 바로 실행된다 → 이름을 불러야 실행된다.
- 괄호 안 이름(`point`, `temp`)은 바깥의 같은 이름 변수와 같은 것이다 → 부를 때 넣은 값이 들어가는 자리다.
- `return` 대신 `print`를 써도 같다 → `print`는 화면에 보여 줄 뿐이라 `check_range(...) == "범위 밖"` 비교가 늘 거짓이 되고 개수가 0건이 된다.
- "범위 밖" = 불합격 → 기준 밖 12건 중 실제 불합격은 3건. 연습용 기준으로 본 판정과 실제 검사 결과는 다르다.
- 설비 한 대가 모든 공정을 한다 → 이 데이터의 설비↔공정 짝은 교육용 가상이다. 실제로는 설비마다 맡는 공정이 정해져 있다.
- `is greater than 80`에 80이 포함된다 → 초과라서 빠진다. 이상은 `is at least`.

## 막히는 지점 TOP3와 대처

1. **`for` 세기와 문제 2(빈칸 없는 전이 문제)** — 세는 변수를 어디서 0으로 두는지, 한 바퀴에 무엇이 바뀌는지 감이 안 온다. 3단계 한 바퀴씩 `print` 셀의 출력을 다시 짚고, 3단계 코드를 옆에 띄워 "이름만 바꾸기"(`pass_count` → `in_count`, `score` → `temp`, `>= 80` → `295 <= temp <= 305`)를 시킨다. `pass_count`를 그대로 베끼면 3단계 값(3)이 섞여 오류 없이 엉뚱한 숫자가 나온다.
2. **노트북 7단계 문제 3의 빈칸 두 개(`check_range(____) == ____`)** — 첫 빈칸에 `record`만 넣으면 `TypeError: '<=' not supported between instances of 'int' and 'dict'`가 난다. `temp`를 넣으면 더 위험하다 — 문제 2의 `for`가 남긴 마지막 값(312.4)이 그대로 들어가 오류 없이 30건이 나온다(조용한 오답). "함수에 넣을 것은 지금 꺼낸 기록의 온도 → `record["온도_C"]`"로 2차시 딕셔너리를 상기시킨다. 3-1을 안 채우고 실행하면 3-2·3-3에서 `NameError: name 'check_range' is not defined`가 난다 — 철자가 아니라 위 셀부터 확인하게 한다.
3. **Orange Select Rows 조건 만들기** — Select Rows는 Transform 묶음에 있고, 이어 붙이는 순간 조건 한 줄이 이미 있다. Add Condition부터 누르면 빈 줄이 남는다(숫자는 맞지만 화면이 다르다). `is outside`는 왼쪽에 작은 값을 넣는다. 안 되면 `_done.ows`를 열어 완성된 조건을 보여 준다.

## 실습 중 오류 대응

- `SyntaxError: expected ':'`: `if`·`else`·`for`·`def` 줄 끝 콜론을 빼먹었다.
- `IndentationError: expected an indented block after 'if' statement on line 2`: `if` 아래 줄을 들여 쓰지 않았다(줄 번호는 코드마다 다르다).
- `IndentationError: unexpected indent`: 들여쓰기가 들쭉날쭉하다. 칸 수를 맞춘다.
- `SyntaxError: invalid syntax. Maybe you meant '==' or ':=' instead of '='?`: 비교에 `=` 하나를 썼다.
- `NameError: name 'check_range' is not defined`: 3-1 함수 셀을 채우고 실행하기 전에 아래 셀을 실행했다.
- `TypeError: '<=' not supported between instances of 'int' and 'dict'`: 함수에 딕셔너리(`record`)를 통째로 넣었다. `record["온도_C"]`로 온도만 꺼내 넣는다.
- `NameError`(예: `scores`, `judge_score`, `records`): 위 셀을 건너뛰었다. Kernel → Restart Kernel and Run All Cells…로 맨 위부터 다시 실행한다(첫 빈칸에서 멈추는 것은 정상).
- `NameError: name '____' is not defined` 또는 `SyntaxError`: 빈칸을 안 채우고 실행했다. 밑줄 개수와 상관없이 필요한 만큼 쓴다.
- 따옴표 빠짐(`== 범위 밖`): `SyntaxError`가 난다(글자 사이 빈칸 때문). 따옴표로 감싼다.
- 결과가 `None`이나 0건: 함수에서 `return`을 빼먹었다(오류 없음).
- 문제 2 결과가 0개·1개이거나 너무 큼: 세는 변수를 `for` 안에 두었거나 `pass_count`가 섞였다(오류 없음).
- Orange File 위젯에 빨간 글씨: 키트 폴더 구조가 바뀌었거나 `.ows`를 키트 밖으로 옮겼다. 키트를 다시 풀고 `_start.ows`를 다시 연다.
- 커널 끊김: 커널 재시작 후 맨 위부터 다시 실행.
